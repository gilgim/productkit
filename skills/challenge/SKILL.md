# Requirement Challenge

Use the installed ProductKit workspace and CLI. The CLI does not call an LLM; you perform the semantic review.

1. Establish and state the scope. Default scope is every current modeled NodeGroup. Record exclusions and why they were not reviewed. **Order: submit every Finding (step 7), have the user confirm or reject each one, save every ImpactReport you will cite (`productkit graph impact --node <id> --output product/graph/reports/<id>.yaml`), and only then run `productkit challenge review-start`** — a run snapshots its inputs, and a Finding added or confirmed afterwards, or a new ImpactReport, makes it stale (a Finding resolved later by `productkit decide resolve` does not). Promote every `finding_candidates` entry from the Clarifications into a Finding with `candidate_refs: [{clarification_ref, index}]`; the gate blocks until each candidate is a Finding the user has confirmed.
2. Read current Prompt, Clarification, NodeGroup/Nodes, Graph Edges and RelationCandidates, ImpactReports, existing Findings, and Change 02–04 structural validation output. Fix no upstream gate here and do not repeat its structural algorithm.
3. Review missing requirements and exceptions, policy conflicts and duplicates, and impact coverage. Compare applicability before calling constraints conflicting.
4. Review normal behavior, then exception, failure, and boundary flows. Inspect AND/OR, condition scope, and precedence. Do not invent product decisions for missing boundaries.
5. Compare Prompt → Clarification → Node meaning, including actors, conditions, outcomes, exceptions, and logical operators. Inspect Graph relation meaning/direction and possible omitted impact candidates.
6. For each plausible issue, write a counterexample as a hypothesis unless observed evidence proves it. Distinguish evidence from inference and record uncertainty and the question a user or later Decision must answer.
7. Submit a typed Finding YAML with `productkit challenge finding add --input <file>` — exact shape from `productkit schema finding` (`issue_key`, `type`, `severity`, `statement`, `related_refs` as `[{kind, ref}]`, `evidence_refs` as `[{kind, ref, detail}]`, `counterexamples`, `ai_assessment`, `questions`, optional `candidate_refs`). New Findings are always `proposed` and `unresolved`. Do not confirm, reject, resolve, defer, or dismiss on the user's behalf. Confirmation is `productkit challenge finding confirm <id> --response confirmed|rejected --rationale <r>` with no `--user-statement`: the CLI reads the user's words from the terminal, which you do not have — hand the command to the user. Only a confirmed Finding can hold a Node out of the Definition or anchor a scope exclusion.
8. Checkpoint all eight areas with `productkit challenge review-area <review-id> <area> --status reviewed --evidence node:NOD-001-1 ...` (or `not_applicable --rationale ...`). A `reviewed` area with no `--evidence` leaves the run incomplete; cite what you actually inspected, and each area needs evidence of these kinds: `missing_requirements_exceptions` prompt + (node or clarification); `policy_conflicts_duplicates` policy or node (`not_applicable` only while no Policy exists); `flow_gaps` node or clarification; `condition_operator_consistency` node + (prompt or clarification); `graph_relation_risks` edge/relation_candidate/node_group/node; `prompt_node_fidelity` prompt + node; `verifiability` node; `impact_coverage` impact_report (saved with `--output`). `review-validate` and `review-complete` take `--review <id>`; without it the CLI picks the last run, which may be a stale one. Areas: `missing_requirements_exceptions`, `policy_conflicts_duplicates`, `flow_gaps`, `condition_operator_consistency`, `graph_relation_risks`, `prompt_node_fidelity`, `verifiability`, `impact_coverage`.
9. Report unreviewed scope, missing inputs, uncertainty, proposed Finding count, confirmed/rejected counts, and open Critical Findings. A Critical Finding blocks approval until it is closed by `productkit decide resolve <DEC>` (content Decision, applied and verified) or by a scope_exclusion Decision with an exclusion item; filing it as `major` to get past the gate is a lie. Finish with `productkit challenge review-complete <review-id>` only after every area is covered. A complete review means coverage was recorded; it does not prove semantic correctness, resolve Findings, or approve the Product Definition.

If interrupted, resume with `productkit challenge review-resume <review-id>` only while the input snapshot is current. Changed input makes the previous review stale; preserve it and start a new review. Never state that all issues were found. Keep possible counterexamples and demonstrated defects distinct.
