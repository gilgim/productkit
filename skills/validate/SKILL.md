# ProductKit Validation & Approval

Use this skill after Change 07 has produced a draft Product Definition.

1. Run `productkit validate` and inspect every blocking, warning, stale, and unreviewed input.
2. Read the current Definition, Journey, Policy, Findings, Decisions, Applications, Graph/Impact reports, Assumptions, and current ChallengeRun.
3. Review the eight required areas: requirement completeness, user flow, policy consistency, acceptance criteria, assumptions, graph/impact, traceability, and counterexamples. An area marked `reviewed` must cite at least one product artifact in `evidence_refs` (Definition, Node, Finding, Decision, Policy, Journey, ImpactReport, ChallengeRun, Prompt). The skill file and the workspace fingerprint are not evidence. The CLI refuses a review with an empty or skill-only `evidence_refs`; it does not check that the cited artifact is the right one for that area — that is on you.
   State the reviewed scope and every item not reviewed in `unreviewed_scope`. Do not move an unreviewed item into `uncertainty` to make `unreviewed_scope` empty; readiness that rests on a redefined scope is not readiness. Compare the Definition against the Prompt text directly, not only against the Nodes; `source.coverage` and `definition.node_coverage` catch structural omission, not a span dispositioned as non_requirement by mistake or a distorted item.
4. For each suspected defect, separate observed evidence from a hypothetical counterexample. Submit it through the existing Finding process; do not set Finding resolution or claim all defects were found.
5. Write the review input — exact shape from `productkit schema semantic-review`, **without** `id` and `content_hash` (the CLI computes them) but **with** `created_at` (ISO time); `definition_hash` is the `content_hash` line of `product/definition.yaml`; `input_fingerprint` and every evidence hash come from `productkit hash fingerprint`. It must carry: one `item_fidelity` entry per (Definition item × source Node) pair with `verdict: same|narrower|broader|contradicts` and a reason (compare the two texts; `contradicts` blocks, a blanket "all same" written without reading is a lie you sign N times); `evidence_refs` per area of the kinds that area is about (requirement_completeness: Prompt + Definition/Node; graph_impact: ImpactReport; traceability: Decision + Prompt; counterexamples: Finding/ChallengeRun; acceptance_criteria: Definition; user_flow: Journey/Node/Definition; policy_consistency: Definition/Node and, if Policies exist, a Policy); `not_applicable` only for `policy_consistency` when no Policy exists and `assumptions` when no Assumption exists; `unreviewed_scope` naming what you did not review; and, if an earlier review of this Definition listed something as unreviewed, either keep it there or put it in `unreviewed_scope_resolved` with evidence. Bind to the current Definition hash and fingerprint. Record it with `productkit validate review --input <yaml>`; do not claim this proves semantic correctness.
6. Re-run `productkit validate --review <id>`. Report machine status separately from semantic assessment. Never create or imply user approval.
7. Approval is the user's, not yours. Under `attestation: flag` in `product/config.yaml` (the `init` default), ask the user for their approval in the conversation and pass the reply verbatim: `productkit approve record --validation <id> --scope <scope> --user-statement "<verbatim response>"`; the report carries a warning. Under `attestation: tty`, show the user `productkit approve record --validation <id> --scope <scope>` (no `--user-statement`) and stop: the CLI reads the statement from the user's terminal, and run by you it fails with "No terminal is attached", which is the intended outcome. Never edit that config line. If no user response exists, stop with approval missing.

The CLI validates schemas, references, and hashes. It cannot authenticate the speaker or establish that a user's statement is true. A PASS is not evidence of semantic completeness.
